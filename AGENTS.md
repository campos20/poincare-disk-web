# AGENTS.md

Guidance for AI coding agents working in this repository.

## Commands

```sh
npm install
npm run dev            # dev server at /poincare-disk-web/ (vite.config.ts base path)
npm test                # vitest run — src/**/*.test.ts only (engine + view, node env)
npx vitest run <path>   # a single test file, e.g. src/engine/tools.test.ts
npx vitest run -t "<name substring>"   # a single test by name
npm run coverage        # vitest run --coverage
npm run lint             # eslint .
npx prettier --check .   # formatting check (CI runs this, not `npm run lint`)
npm run build             # tsc -b && vite build — the only place typechecking runs in CI-equivalent form
```

CI (`.github/workflows/test.yml`) only runs `prettier --check` and `npm run coverage`
on PRs — it does **not** run `tsc -b` or `eslint`. Run both yourself before
considering a change done; nothing else will catch a type or lint error.

`tsconfig.app.json` has `noUnusedLocals`/`noUnusedParameters` on, so an unused
import or variable is a build failure, not just a lint warning.

## Architecture

Three-layer split, in dependency order — each layer only imports from the ones
before it:

- **`src/engine/`** — framework-agnostic TypeScript, zero React/DOM imports.
  The object model (`types.ts`), pure state operations (`construction.ts`),
  and tool state machines (`tools.ts`). Re-exported through `engine/index.ts`;
  import from `"../engine"`, not the submodules directly.
- **`src/view/`** — React + SVG rendering, coordinate conversion, and the
  `appState.ts` reducer that wires user intents to engine calls.
- **`src/routes/`** — TanStack Router file-based routes (`routeTree.gen.ts` is
  generated by the `@tanstack/router-plugin` Vite plugin on dev/build — don't
  hand-edit it; adding/removing a file under `src/routes/` regenerates it).

### Entity model (`engine/types.ts`)

Only points (`FreePoint`, `IntersectionPoint`) carry coordinates. Every other
entity (`Segment`, `Line`, `Circle`) references point ids, never copies
coordinates — so dragging a point updates every dependent at render time for
free, and `deleteEntity` cascades by walking those id references transitively
(repeated sweeps until a pass finds nothing new — see its doc comment).
`IntersectionPoint` coordinates are derived, not user-set: `exists: false`
means its two source curves currently don't cross, and its x/y are left at
their last position rather than guessed — `exists`, not the coordinates, is
what callers must check.

### Tool state machine (`engine/tools.ts`)

Tools accumulate clicked point ids in `ToolState.buffer` until they have
enough (`TOOLS[tool].pointsNeeded`), then `applyClick` creates the entity and
resets the buffer. Clicks snap to an existing point within `SNAP_THRESHOLD`
(`acquirePoint`) rather than stacking a duplicate. The `intersect` tool is
declared here for the toolbar's sake but its actual two-click buffering lives
in `view/appState.ts`'s `entityClick` action instead — it picks curves by what
was clicked (DOM element), not by coordinate, which needs geometry the engine
doesn't have.

### The engine/view split for geometry

The engine never computes geometry. Two callback seams inject it from the
view layer at the two points the engine needs it:

- `recomputeIntersections(construction, compute)` — `compute` is
  `view/intersections.ts`'s `computeIntersectionPoint`.
- the `intersect` tool's entity-vs-entity math — `view/intersections.ts`'s
  `intersectEntities`, called from `appState.ts`.

`view/naming.ts` (display names for points/entities) is presentation split
the same way: the engine only knows ids.

### Hyperbolic rendering — already done, despite what some comments say

The disk is modeled in `view/disk.ts` as the unit disk (center origin, radius
1 in model space); `DISK_RADIUS` there is only the on-screen pixel radius.
`view/hyperbolicFormulas.ts` has the actual Poincaré-disk math (geodesics as
circles orthogonal to the unit circle, etc.), and `view/renderEntity.tsx`
already calls into it directly for segments/lines/circles.
`view/intersections.ts` is the geometric counterpart (curves → crossing
points instead of points → curve) and is also hyperbolic-aware.

**`view/geometry.ts` is now mostly dead code** — only its `segmentShape` is
still used (for the degenerate diameter case in `renderEntity.tsx`'s
`hyperbolicPath`); `lineShape`, `circleShape`, and `clipLineToRect` have no
production callers left. Its own doc comment (and the README, and
`hyperbolicFormulas.ts`'s doc comment) still describe it as the pending "swap
point" for a future Euclidean→hyperbolic migration — that migration already
happened. Don't be misled by those comments into thinking Euclidean
rendering is still live or that geometry.ts needs touching for hyperbolic
work; go to `hyperbolicFormulas.ts` and `renderEntity.tsx` instead.

### i18n

`src/i18n/messages.ts` defines `MessageKey` from the `en` object's keys, and
types `pt` as `Record<MessageKey, string>` — so an untranslated or misspelled
key is a compile error, not a silent runtime fallback. Add new UI strings to
both locales.

### Deployment

Pushes to `main` deploy to GitHub Pages (`.github/workflows/deploy.yml`).
Pages has no server-side fallback, so `dist/index.html` is copied to
`dist/404.html` at deploy time to make deep links work with TanStack Router's
client-side routing (`basepath: import.meta.env.BASE_URL` in `main.tsx`).
